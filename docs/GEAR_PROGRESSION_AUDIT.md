# Fishing System 2.0 Gear Progression Audit

Updated: 2026-09-04

## Scope

This document audits the existing Fishing System 2.0 equipment paths on `dev` before any post-2.0 gear redesign.

Audit baseline:

- branch: `dev`
- source head inspected: `465259e04580e14a2aed7d0d228e56dc7350a85a`
- Minecraft: 1.21.1
- Tide runtime target: 2.1.1
- Fishing System 2.0 contract: `docs/FISHING_SYSTEM_2_SPEC.md`
- current-state source: `docs/CURRENT_STATE.md`
- backlog source: `docs/TODO.md`

This pass is documentation-only. It does not change item registrations, modifiers, catch selection, specimen generation, bite timing, minigame behavior, Satchel behavior, networking, persistence, or UI behavior.

The historical `docs/FISHING_SYSTEM_2_BALANCE_REPORT.md` is useful as a regression record, but current source wins where the old Stage 64 report differs from the live 2.0.1 implementation. Two important examples are documented below:

- the old report's Steel Leader protection values predate the current four-tier leader model;
- the old report's three-bait matrix predates Tide 2.1.1's bait/accessory rework.

## Runtime stage terminology

| Stage | Meaning in this audit |
| --- | --- |
| Eligibility | Whether a catch can occur in the current dimension, fluid, biome, temperature, time, depth, weather, or other Tide context. |
| Fish selection | Relative fish/crate weighting or catch-pool restriction after eligibility is known. |
| Specimen generation | Canonical percentile, physical size, Body Type, Condition, Pigmentation, Specimen Quality, Trait Luck, and FishScore construction. |
| Bite timing | Time before the hook enters the catch/minigame flow. |
| Fight behavior | Catch-zone geometry, minigame speed/tempo, strength, line behavior, and related fight projections. |
| Retrieval | Post-fight catch loss prevention, catch delivery, and post-retrieve effects. |
| UI/post-catch | Tooltip/display/config projection, Satchel storage, protection, sorting, Journal projection, and other behavior after canonical catch state already exists. |

## Executive findings

1. Gear behavior currently has three owners rather than one unified gear service:
   - Tide 2.1.1 owns native rod, hook, line, bait, environmental, and bait-stack behavior.
   - Fishing System 2.0 owns canonical `FishingGearRegistry`, `FishingGearModifiers`, species-selection weighting, Trait Luck input, fight projections, leader effects, Leviathan Bait modifiers, and selected Tideborne accessory behavior.
   - Team Journal and TideTraits still provide config/UI/post-catch adapters, most notably bobber Fishing Luck/Lure mutation and Satchel behavior.

2. No audited gear directly writes canonical natural percentile, FishScore, base length, final length, final percentile, Condition, Pigmentation, or Specimen Quality. Fishing Luck reaches species selection. Trait Luck reaches `SpecimenGenerator`. Physical and score values are then generated by the canonical specimen pipeline.

3. The modifier schema can represent Body Type chance multipliers, so the API is capable of influencing a canonical trait probabilistically. None of the currently registered audited gear profiles populates that map.

4. Bobbers have duplicated modifier ownership:
   - `tideteamjournal.BobberBonuses` plus its Tide hook mixin applies configurable Fishing Luck and lure speed.
   - `tideboundcompatibility.fishing.BobberGearModifiers` applies selected canonical V2 fight, Trait Luck, crate, and catch-loss modifiers.
   The same item can therefore be read by two independent systems.

5. Line behavior is also split:
   - Tide owns native line accessory behavior.
   - Tideborne projects line identities into canonical fight multipliers and supports optional Tideborne/Myths line items.

6. `tidebound_compatibility:steel_leader` is a stable compatibility ID even though the current tier name is Iron Leader. Renaming the registry ID would break persisted gear and migration assumptions.

7. Leviathan Bait is intentionally split between selection and canonical modifier paths. It forces a fish-only selector through a Tide integration adapter and separately contributes Fishing Luck, Trait Luck, Strength, and Tempo.

8. The upgraded Satchel is not a catch-generation author. Its fishing path intercepts delivery after Tide has selected/caught a fish, then stores, protects, sorts, or falls back to normal spawning. It reads canonical/legacy specimen metadata but does not reroll a canonical specimen.

## Canonical modifier and identity layer

### `FishingGearModifiers`

`com.redslovesgames.tideborne.fishing.v2.FishingGearModifiers` is the composable modifier record used by the V2 layer.

It contains:

- additive `fishingLuck`;
- additive `traitLuck`;
- multiplicative `strengthMultiplier`;
- multiplicative `tempoMultiplier`;
- category and catch-pool restrictions;
- per-Body-Type probability multipliers;
- named additive modifiers;
- named multiplicative modifiers.

Composition adds luck and named additive values, multiplies fight/body-type/named multipliers, intersects allow restrictions, and unions deny restrictions. This is the most important existing modifier-composition API to preserve.

### `FishingGearRegistry`

`com.redslovesgames.tideborne.fishing.v2.FishingGearRegistry` is the exact namespaced identity registry. It should remain the stable identity/query boundary instead of spreading new string or item-instance checks.

Current slots:

- `ROD`
- `LINE`
- `HOOK`
- `BAIT`
- `ATTACHMENT`
- `BOBBER`

Important query APIs to preserve:

- `resolve(ItemStack)`
- `resolve(Item)`
- `resolveId(Identifier)`
- `registeredId(profile)`
- `matches(...)`
- `profiles()`
- `supportedBobberIds()`
- `isSupportedBobberId(...)`
- `isSupportedBobber(...)`
- `resolveSlot(...)`

## Bobbers

### Shared bobber path

All 32 supported bobber IDs are centralized in `FishingGearRegistry.supportedBobberIds()`.

Two independent modifier layers can apply:

1. `tideteamjournal.BobberBonuses`
   - reads bobber config by registry ID;
   - mutates TideFishingHook `luck` and `lureSpeed` at hook construction;
   - `luck` affects Tide fish selection;
   - `lureSpeed` affects bite timing;
   - tagged third-party bobbers fall back to a configurable/default bonus.

2. `tideboundcompatibility.fishing.BobberGearModifiers`
   - applies selected V2 Trait Luck, fight, crate-weight, and catch-loss effects;
   - uses a hard namespace/path switch.

The duplicated ownership is intentional legacy layering today, but it should not be expanded during future redesign.

## Leviathan equipment logic

Leviathan behavior currently spans several components.

### Eligibility/gating

`LeviathanBaitFishing.isEnabledFor(...)` requires:

- Myths integration active;
- Leviathan support enabled by config;
- Leviathan Bait attached to the rod through Tide's bait system.

The bait check is a direct item check against `TideboundItems.LEVIATHAN_BAIT`.

### Fish-only selection

`LeviathanBaitRules.selectCatch(...)` chooses between:

- the standard Tide selector; or
- a fish-only selector when Leviathan Bait's category restriction is active.

The compatibility `TideFishingHookMixin` redirects Tide selection into this adapter and tracks whether the selected result came from the Leviathan fish-only path so Tide's normal empty-result fallback cannot silently reintroduce a non-fish catch.

This is selection behavior, not specimen authoring.

### Canonical modifiers

`TideborneFishingGearModifiers.forLeviathanBait(...)` contributes:

- Fishing Luck `+15`;
- Trait Luck `+4`;
- Strength `1.25x`;
- Tempo `1.20x`;
- category allow restriction for `fish`.

Fishing Luck affects species weight. Trait Luck is consumed by canonical specimen generation. Strength and Tempo affect the fight.

### Boss/Leviathan encounter projection

The historical deterministic Stage 64 regression matrix records core rod encounter scores:

- Wood: `0.80`
- Iron: `0.98`
- Gold: `0.90`
- Diamond: `1.20`
- Netherite: `1.38`

It also records a Leviathan setup factor of `1.55`, making Diamond and Netherite the first core rods to clear that historical boss threshold while Iron remains below it.

These values are retained here as the existing regression projection. They should not be promoted into a second runtime gear authority unless the later redesign deliberately centralizes them.

### Catch interception path

The TideTraits `TideFishingHookMixin`:

1. lets Tide select and log the catch;
2. can defer the caught fish entity when an enabled Auto Stow target exists;
3. inserts the catch into `AnglersSatchelStorage`;
4. applies automatic protection and organizer behavior after insertion;
5. falls back to normal entity spawning if storage fails.

This is a retrieval/post-catch path.

### Canonical state behavior

`SatchelAutomaticProtection` and sorting/detail helpers read existing values such as:

- canonical or migrated specimen metadata;
- percentile/size metadata;
- rarity;
- record state;
- trait axes.

They do not generate a second canonical specimen and do not directly write FishScore or natural percentile.

A nearby historical `CatchTraitService.individualizeNewCatches(...)` call remains in the TideTraits Tide hook mixin for legacy/noncanonical catch compatibility. That path is capable of writing legacy trait/size state and therefore must remain guarded from canonical V2 catches. It is not an upgraded-Satchel modifier and should not be confused with Auto Stow itself.

## Direct Fishing Luck access

Current direct Fishing Luck paths found in this audit:

1. Tide native rod/bait cast path:
   - aggregates bait luck through `BaitUtils`;
   - applies enchantment/native rod luck;
   - Lucky Bait contributes `+2`;
   - Tide's luck-boosting rod identity/tag contributes native luck.

2. Team Journal bobber mixin:
   - `tideteamjournal.mixin.TideFishingHookMixin`;
   - reads `BobberBonuses`;
   - directly increments TideFishingHook's `luck` field.

3. Leviathan Bait:
   - `FishingGearModifiers.fishingLuck = +15`;
   - consumed by Fishing System 2.0 species weighting.

Canonical consumption occurs in `SpeciesSelectionService.adjustedWeight(...)`. It changes relative species selection weight, not specimen percentile.

## Direct Trait Luck access

Current direct gear Trait Luck paths:

- `tide:amethyst_bobber`: `+1`;
- `tide:echo_bobber`: `+2`;
- `tidebound_compatibility:leviathan_bait`: `+4`.

Trait Luck is consumed by `SpecimenGenerator`. It can change probabilities for canonical random trait outcomes because it is an input to the canonical generator, but gear does not directly assign the resulting trait or percentile.

Perfect Catch's temporary `+10` Trait Luck is also part of `SpecimenGenerator`, but it is a catch-performance rule, not equipment.

## Canonical specimen mutation audit

### Current audited gear does not directly author

No audited gear path was found that directly sets:

- natural specimen percentile;
- base length;
- final length;
- final percentile;
- FishScore;
- Body Type result;
- Condition result;
- Pigmentation result;
- Specimen Quality result;
- mutation seed;
- canonical specimen seed.

### Indirect canonical influence

Gear can influence canonical outcomes only through defined inputs:

- Fishing Luck changes species-selection weights before a specimen exists.
- Trait Luck changes trait probabilities inside `SpecimenGenerator`.
- the `FishingGearModifiers` type can carry Body Type chance multipliers, although no currently audited registered gear profile uses them.

### Canonical ownership

- `SpeciesSelectionService` owns canonical species weighting/selection inputs.
- `SpecimenGenerator` owns canonical specimen construction.
- `FishScoreV2Service` owns FishScore calculation after canonical traits/physical size are finalized.
- `CanonicalCatchStateManager` guards catch lifecycle state and legacy compatibility boundaries.

The future gear pass should preserve these ownership boundaries. Gear may provide inputs but should not become a second specimen author.

## Redesign constraints established by this audit

This audit does not choose new archetypes, balance values, or gear progression. It establishes the boundaries the next step must respect:

- keep specimen generation server-authoritative;
- do not let equipment directly set FishScore, percentile, canonical trait results, or physical size;
- prefer `FishingGearRegistry` and `FishingGearModifiers` over new ad hoc item checks;
- preserve exact registry IDs and migration-sensitive components;
- preserve Tide native eligibility semantics unless the later design explicitly changes an eligible gear effect;
- consolidate duplicated modifier ownership only with regression coverage for both layers;
- treat Tide-targeting gear mixins as version-sensitive adapters;
- keep Satchel upgrades post-catch unless a future design explicitly specifies a new fishing input;
- do not infer current balance from obsolete Stage 64 values when current source has superseded them.
